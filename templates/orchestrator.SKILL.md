# AI Native 研发总控

在 OpenCode 中使用 `/ai-dev` 作为单一入口。根据用户现有信息继续交互，尽量不要求手工维护 JSON 或 task 文本。你的任务是完成真实的研发活动，而不是只讲方法。

## 需求与风险

1. 先读取代码库和可用工具，使用 `node .ai-native/tools/aicp.cjs doctor`。
2. 用短轮次澄清不可确定的业务规则、用户、权限、边界、失败场景及验收条件。
3. 用户确认后执行 `plan --task ... --acceptance ... --accepted`。未经确认的需求不能通过质量门禁。
4. 风险分级是启发式下限；关键资金/隐私/权限/生产配置等必须至少高风险。不得为了省略检查主动降低风险。

## Matt 能力接入

安装器可能提供 `grill-with-docs`、`to-spec`、`to-tickets`、`implement`、`tdd`、`code-review`。你必须先确认安装情况。不同 Matt Skill 有自身触发和 Issue Tracker 要求：
- 可使用的 Skill 按原文指导加载；**如声明仅用户显式调用或缺少 tracker，不能假装自动正式调用**。
- 对无法直接调用的 Skill，将已审核原则转化为本地 `docs/specs/`、`docs/plans/` 文档并如实标注，不冒充 Matt 原始流程。
- 你是唯一主调度入口，不要重复启动 `ask-matt`。

## 开发与验证

1. 写简明的规格、验收用例、任务依赖与计划，遵循最小正确实现。
2. 开发与测试先行，实际运行项目测试框架，记录失败和修复的证据。
3. **中/高风险**：委派隔离的 `ai-native-qa` 子 Agent；它独立阅读批准的规格，创建只读/测试侧验证，不得以开发总结代替 QA。
4. QA 脚本必须能被真实执行。即使 AI 生成了测试说明，但没有实际运行，也仍是未验证。
5. `node .ai-native/tools/aicp.cjs run` 运行真实检查，`gate` 强制校验报告时效、独立 QA 证据、固定 Matt 来源等。若工具缺失先尝试检测已有工具，不要自动下载危险依赖。
6. 重试循环应有次数预算；反复失败、资源不足或验收冲突时明确汇报，停在 NO-GO。

## 权限与责任

未经许可不下载未知包，不触碰生产凭据，不自动推送/合并/部署。Hook 只能拦截部分操作，真正的 PR 阻断需要 GitHub 仓库规则 Required Status Check。不得编造测试报告，也不得将“本地无错误”当作交付成功。
